# FlowDesk-React

Frontend for **FlowDesk**, a mini Jira-style project management tool (programs, tasks, teams, comments). It talks to the FlowDesk API (Express) at `http://localhost:3001`. The API contract is published at **`http://localhost:3001/openapi.json`** (Swagger UI on the same host).

## Stack

| Concern | Choice |
|---|---|
| Build / dev server | Vite 8 |
| UI | React 19 + TypeScript (strict) |
| Routing | React Router v7 (declarative mode) |
| Server state | TanStack Query v5 |
| HTTP client | `openapi-fetch`, typed by `openapi-typescript` output |
| Components / styling | shadcn/ui (source in `src/components/ui`) + Tailwind CSS v4 |
| Forms | react-hook-form + zod (UX validation only; the backend is authoritative) |
| Google sign-in | `@react-oauth/google` (Google Identity Services) |
| Toasts | sonner (via shadcn) |
| Lint | oxlint |

Don't add another UI kit, HTTP client, state library or CSS approach without asking.

## Environment

Vite exposes only `VITE_*` variables, and **everything in them ships to the browser**. Never put a secret in one: no Google client secret, no JWT secret, no DB URL.

| Variable | Required | Example | Purpose |
|---|---|---|---|
| `VITE_API_BASE_URL` | yes | `http://localhost:3001` | FlowDesk API base URL |
| `VITE_GOOGLE_CLIENT_ID` | yes | `1234-abc.apps.googleusercontent.com` | Public OAuth client ID. Must be the **same** client as the backend's `GOOGLE_CLIENT_ID`, or `POST /auth/google` fails with `INVALID_GOOGLE_TOKEN` |

- Read and validate them in one place, `src/config/env.ts`, and fail fast on startup if one is missing. Nothing else reads `import.meta.env` directly.
- Real values go in `.env.local` (gitignored by `*.local`). Commit `.env.example` with placeholders.
- The backend's `APP_BASE_URL` must be this frontend's origin (`http://localhost:5173` in dev), because invite emails link to `{APP_BASE_URL}/invites/accept?token=…`.

Request flow: **page/component → feature hook (`features/*/api.ts`) → `apiClient` (`src/api/client.ts`) → backend.** Components never call `fetch` or `apiClient` directly, and features don't import each other's internals; shared code moves to `components/`, `lib/` or `api/`.

## 1. Backend API contract

- `/openapi.json` is the **single source of truth**. Read the operation (path, method, request schema, response schema, **description**, every response code) before implementing any call. Auth requirements, roles and error codes are written in each operation's description and response descriptions.
- Run `npm run api:types` before starting each feature so `schema.d.ts` matches the running backend.
- **Never invent** endpoints, methods, request fields, response fields, status codes or error codes. Never assume a response shape that isn't in the contract.
- Don't re-implement backend business logic in the frontend (role checks, date rules, dependency rules, domain checks). Call the API and render its answer.
- If the contract is missing something, is ambiguous, or disagrees with the backend's actual behaviour, **stop and report it** (what, where, what you expected). Don't work around it silently, and don't change the backend to make the frontend easier.

## 2. API integration

- **One client.** `src/api/client.ts` creates `createClient<paths>({ baseUrl: env.VITE_API_BASE_URL })` with middleware that:
  - attaches `Authorization: Bearer <accessToken>` when a token exists, plus `Content-Type: application/json` on bodies;
  - on **401** (`AUTH_REQUIRED` or `INVALID_AUTH_TOKEN`) clears the session and the query cache, then sends the user to `/login?redirect=<current path>`. This doesn't apply to `POST /auth/google` itself, whose 401s are login errors.
- **Types come from the contract.** Use `paths[...]` and `components["schemas"][...]` from `schema.d.ts`. `features/*/types.ts` may only alias them (`type Employee = components["schemas"]["Employee"]`).
- **Response envelopes** (from the contract): single resources are `{ data: T }`; lists are `{ data: T[], meta: { total, limit, offset } }` with `limit`/`offset` query pagination; `DELETE`s mostly return **204** with no body. `POST /invites/accept` also returns `message`.
- **Error shapes** (from the contract):
  - `ErrorResponse`: `{ error: string, code?: string, details?: unknown }` for 400-with-code, 401, 403, 404, 409, 410, 500 and 502.
  - `ValidationErrorResponse`: `{ error: "Validation failed" | "Malformed JSON body", details: { path, message }[] }` for schema violations.
  - `src/api/errors.ts` turns both into one `ApiError { status, code?, message, fieldErrors?, details? }`. Branch on `code` first, then `status`. Never parse `error` strings.
- **Every screen handles these states:**

  | State | Handling |
  |---|---|
  | loading | skeleton / `PageLoader`; disable submit buttons while a mutation is pending |
  | success | render data; toast on mutations |
  | empty | `EmptyState` with the next action if the user's role allows it |
  | 400 validation | map `details[].path` onto the form fields; show anything unmatched as a form-level error |
  | 400/409/410 with `code` | user message from the code map in `errors.ts` (e.g. `EMPLOYEE_EXISTS`, `INVITE_EXPIRED`, `TASK_BLOCKED` with `details.blockers`) |
  | 401 | session cleared, redirect to login (client middleware) |
  | 403 `FORBIDDEN` | `ForbiddenState` or toast; don't retry |
  | 404 | `NotFoundState` |
  | 5xx / 502 | `ErrorState` with retry; 502 `GOOGLE_UNAVAILABLE` / `EMAIL_DELIVERY_FAILED` say "try again" |

- TanStack Query: one query-key factory per feature (`inviteKeys`, `employeeKeys`, …). Invalidate the affected keys after a mutation. Don't retry 4xx responses.
- The frontend never talks to the database or any service other than the FlowDesk API and Google Identity Services.

## 3. Authentication and authorization

**Flow (per the contract):**
1. `/login` renders the Google Identity Services button (`<GoogleOAuthProvider clientId={env.VITE_GOOGLE_CLIENT_ID}>` + `<GoogleLogin>`).
2. On success, send `credential` (the Google **ID token**) to `POST /auth/google` as `{ idToken }`.
3. The response is `{ data: { accessToken, tokenType: "Bearer", expiresIn, employee } }`. Store `accessToken` and `expiresAt = now + expiresIn*1000` in **localStorage** (`tokenStorage.ts`), and put `employee` in auth state.
4. On app boot, if a non-expired token exists, call `GET /auth/me` to revalidate it and get the **current** role. Until that resolves, the auth status is `loading`: show a full-page loader and don't render protected routes.
5. **Logout** is client-side only (the backend has no logout endpoint): clear storage, the query cache and auth state, then go to `/login`.
6. **Expiry:** tokens last 8 hours and there is no refresh. Treat the session as expired when `expiresAt` has passed or on any 401, and redirect to login with a "session expired" message.

**Login errors to show:**

| Status | Code | Message |
|---|---|---|
| 401 | `INVALID_GOOGLE_TOKEN` | Google sign-in failed; try again |
| 401 | `GOOGLE_EMAIL_NOT_VERIFIED` | Google email not verified |
| 401 | `EMAIL_DOMAIN_NOT_ALLOWED` | Use your @saajha.org account |
| 403 | `NOT_INVITED` | You haven't been invited / haven't accepted your invite |
| 403 | `ACCOUNT_INACTIVE` | Account deactivated |
| 403 | `GOOGLE_ACCOUNT_MISMATCH` | This employee is linked to a different Google account |
| 502 | `GOOGLE_UNAVAILABLE` | Google is unavailable; retry later |

**Rules:**
- The backend is authoritative for permissions. `RequireAuth` and `RequireRole` only improve UX: they hide or disable actions the role can't perform. A 403 from the API is always handled even when the UI allowed the action.
- The role always comes from `GET /auth/me` / the login response's `employee.role`. **Never** decode the JWT for the role, read it from the URL or a form, or let the user choose it.
- Public routes are `/login` and `/invites/accept`. Everything else sits under `RequireAuth`.
- The token lives in localStorage, so XSS is the main risk: never use `dangerouslySetInnerHTML` with API or user content, and never log tokens.

### Role matrix (from the contract; UX hints only, the backend enforces)

| Action | ADMIN | MANAGER | MEMBER |
|---|---|---|---|
| Invite member (`POST /invites`) | ✓ | ✓ | ✗ |
| Create employee directly (`POST /employees`) | ✓ | ✗ | ✗ |
| Create / update team, add / remove team members | ✓ | ✓ | ✗ |
| Delete team | ✓ | ✗ | ✗ |
| Create / update program | ✓ | ✓ | ✗ |
| Delete program | ✓ | ✗ | ✗ |
| Create / update tasks, dependencies, comments | ✓ | ✓ | ✓ |
| Delete task | ✓ | ✓ | reporter only |
| Edit comment | author only | author only | author only |
| Delete comment | ✓ | ✓ | author only |

Keep this table in sync with the contract when the backend changes.

## UI conventions

- Use shadcn/ui components from `src/components/ui`; add new ones with `npx shadcn add <name>` instead of hand-rolling. Style with Tailwind utilities and `cn()`.
- Reuse `components/feedback/*` for loading, empty, error, forbidden and not-found states, and sonner toasts for mutation results.
- `AppShell` holds the sidebar navigation, header, user menu (name, role, logout) and an `<Outlet />`. Nav items declare the roles they're shown to.
- Forms: react-hook-form + zod resolver. The zod schema mirrors the contract's documented constraints (lengths, enums, required fields) for instant feedback only; server `details` always win.
- Accessibility: label every input, make buttons real `<button>`s, keep keyboard focus visible.

## 4. Specification-driven development

- Specs live in `.claude/specs/NN-<slug>.md`. Read the feature's spec **and** the relevant contract operations before writing code.
- Implement **one feature at a time**, in the build order below. Don't start the next one until the current one meets the definition of done.
- Reuse shared components, `apiClient`, generated types and the error utilities. Don't duplicate them per feature.
- After implementing, test against the running backend: the success path **and** each documented failure (validation, 401, 403 as a lower role, 404, 409/410 codes, 5xx/502 where you can trigger it).
- At the end of a feature, report missing endpoints, mismatched schemas and any assumptions you made.

### Build order

1. **Contract audit**: inspect every operation; confirm request bodies, responses, auth/roles and error responses are documented; list gaps.
2. **Frontend setup**: Tailwind + shadcn, React Router, TanStack Query, openapi-fetch + generated types, `env.ts`, error utilities, feedback components.
3. **Authentication**: Google login, backend verification, session persistence, `/auth/me` revalidation, logout, protected routes, expiry handling.
4. **App layout**: AppShell, navigation, header, role-aware menus, global loading/error boundaries.
5. **Invitation management**: invite form (ADMIN/MANAGER), public `/invites/accept?token=` page.
6. **Member management**: employee list/detail (filters `role`, `teamId`, `includeInactive`, pagination), team membership.
7. Then: teams → programs → tasks (dependencies, labels) → comments (replies, @mentions).

## Known contract facts and gaps (audited 2026-10-17)

Facts:
- 36 operations across Health, Auth, Employees, Invites, Teams, Programs, Tasks and Comments. Everything except `GET /health-check`, `POST /auth/google` and `POST /invites/accept` needs a bearer token.
- Org email domain is exactly `saajha.org` (subdomains rejected) for both invites and Google sign-in.
- An invite is valid for 72 hours. Re-inviting the same email revokes the previous pending invite. The token is only sent by email and never returned by the API.
- `POST /invites/accept` only creates the employee. The user then signs in with Google separately. Error codes: `INVALID_INVITE_TOKEN`, `INVITE_REVOKED` (400), `INVITE_ALREADY_ACCEPTED`, `EMPLOYEE_EXISTS` (409), and **410** for an expired invite.
- An employee created via `POST /employees` (no invite) **can't sign in** (`NOT_INVITED`), so prefer invites in the UI.
- Tasks are addressed by `taskRef` (id or key such as `MKT-3`).

Gaps (report them and don't work around them; ask the backend before building the UI):
1. **No invite listing / revoke / resend** (`GET /invites` etc. don't exist). "Invitation management" today means only create + accept.
2. **No endpoint to change an employee's role or deactivate them.** "Member management" today means list/view employees + team membership.
3. **No logout, token revocation or refresh endpoint.** Logout is client-side, and users sign in again after `expiresIn` (8 h).
4. The `POST /employees` 409 response has no documented `code` (probably `EMPLOYEE_EXISTS`). Confirm before relying on it.
